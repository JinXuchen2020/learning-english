# AI-107 — 每日 token / 调用配额

> 状态: in-progress | 栈: node-ts (NestJS 10 + TypeORM) | 分支: feat/ai-107（基于 feat/ai-106）

## 1. 目标

为 AI 能力增加「每用户每日配额」闸门：限制单用户每日 AI 调用次数与 token 用量，
超限返回 **429 + 降级标记（degraded）**，避免单用户刷爆额度 / 失控成本。配额数据
持久化到 `ai_usage` 表，可检索、可审计（与 AI-108 日志互补）。

价值：在 M2+ 真正接入 AI 控制器前，先把配额引擎与 provider 外壳就位，使所有
`AiProvider` 消费方（plan / speech / chat / report）免费获得配额保护。

## 2. 接口契约

### 后端（AI-107 新增）
- 实体 `AiUsage`（`ai_usage` 表）：`id`(uuid) / `userId`(varchar, indexed) /
  `date`(varchar `YYYY-MM-DD`, indexed) / `callCount`(int, default 0) /
  `tokenCount`(int, default 0) / `updatedAt`(timestamp)。唯一约束 `(userId, date)`。
- 配置（经 `ConfigService`，默认保守值，不会误伤）：
  - `AI_DAILY_CALL_LIMIT`（默认 **200**）
  - `AI_DAILY_TOKEN_LIMIT`（默认 **100_000**）
- 服务 `AiUsageLimitService`：
  - `getState(userId, now?)` → `QuotaState`（含 `callsRemaining`/`tokensRemaining`/`limited`）
  - `assertWithinQuota(userId, estimatedTokens=0, now?)` → 超限抛 `AiQuotaExceededError`(429 + degraded)
  - `recordUsage(userId, tokens=0, now?)` → 累加并 upsert 当日行，返回新 `QuotaState`
- 错误 `AiQuotaExceededError extends AiProviderException`：`statusCode=429`、`code='QUOTA_EXCEEDED'`、`degraded=true`。
- Provider 外壳 `UsageLimitedAiProvider implements AiProvider`：最外层包装，每次调用前
  `assertWithinQuota`、成功后 `recordUsage`（仅成功计费，失败/重试不计）。`name` 透传。

> 偏离 backlog 原文的 `common/limits.ts`：项目既有 AI 能力统一放在 `server/src/ai/`
> （AI-102~106 已建立此约定），故本 feature 的配额代码同样归入 `ai/`，不另辟
> `common/`，以贴合项目分层约定。

## 3. 数据模型

```sql
CREATE TABLE ai_usage (
  id          VARCHAR(36) PRIMARY KEY,
  userId      VARCHAR(255) NOT NULL,
  date        VARCHAR(10)  NOT NULL,   -- YYYY-MM-DD (UTC)
  callCount   INTEGER NOT NULL DEFAULT 0,
  tokenCount  INTEGER NOT NULL DEFAULT 0,
  updatedAt   TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (userId, date)
);
CREATE INDEX idx_ai_usage_user ON ai_usage(userId);
CREATE INDEX idx_ai_usage_date ON ai_usage(date);
```

TypeORM `synchronize` 在 dev 自动建表；`appEntities` 已登记 `AiUsage`。

## 4. 验收标准
- [ ] `AiUsage` 实体注册、`ai_usage` 表随 schema 同步建立。
- [ ] 配小额配额（如 `AI_DAILY_CALL_LIMIT=2`）连续调用可触发 429（`AiQuotaExceededError`）。
- [ ] token 用量超额同样触发 429（以累计 token 判断）。
- [ ] 配额数据持久化（`findOne`/`save` upsert），跨日自动开新行。
- [ ] `name` 契约不变；配额错误位于最外层、不进入 AI-106 的 `withRetry` 重试。
- [ ] 单元测试覆盖：配置读取 / 状态计算 / 超限分支 / 记账 / 外壳编排（含 inner 抛错不计费）。

## 5. 风险点
- **并发竞争**：read-modify-write 非事务，高并发下同一用户可能短暂超量。本阶段为低流量
  儿童应用，接受弱一致；后续可改 `repo.increment` / 行锁。
- **用户上下文**：当前无 AI 控制器，`UserIdResolver` 默认返回 `'anonymous'`（所有调用计入
  匿名桶）。未来 AI 控制器（AI-20x/30x/40x）落地时，应注入请求级 `UserIdResolver`
  以真正按登录用户隔离配额——本 feature 已预留 `USER_ID_RESOLVER_TOKEN` 扩展点。
- **失败不计费**：仅对「成功调用」记账，避免重试/瞬时错误虚增配额（与 AI-106 重试共存）。
