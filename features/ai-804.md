# AI-804 — 学习计划生成流式显示（Streaming Plan Generation UX）

> 状态: done | 栈: node-ts (NestJS 10 + TypeORM + better-sqlite3 / Next.js 14) | 分支: feat/ai-804
> 来源: 用户诉求（2026-08-18）—「让前端像聊天那样流式显示计划生成过程」。当前 `POST /api/ai/plan/generate` 是**非流式**：provider `chat()` 一次性 `await res.json()` 读完整响应，控制器直接返回整份 `GeneratePlanResponse`，前端在 9~40s 内白屏，体感差；且生产日志显示偶发 JSON 格式噪声误杀（已由 AI-204 的 `extractJson` 增强缓解，但等待体验未解决）。

## 1. 目标

让计划生成过程「可见、可感知」，消除长等待白屏：

1. **实时渐进输出** — 生成期间前端逐步看到 AI「正在构思计划」的流式文本（狐狸老师口吻的进度感，而非裸 JSON），等待不再焦虑。
2. **最终仍校验** — 流仅用于**展示**；服务端必须攒齐完整文本，经 `extractJson` + `validatePlan` 校验后才以 `done` 事件交付结构化计划。**不以中间态 JSON 直接渲染**（避免半成品 JSON 解析崩溃，呼应「出错即抛」口径）。
3. **附带收益：缓解 504 体感** — Vercel 函数流式持续往外吐 SSE 帧，网关不再因「长时间无响应」直接掐断（只要总时长 < maxDuration 60s）；连接存活期间不会 504。

## 2. 现状事实（代码查证）

- `OpenAiCompatibleProvider.chat()` → `postJson()`（`openai-compatible.provider.ts:277-307`）是普通非流式 `fetch` + `await res.json()`，**全仓无 SSE/ReadableStream 消费**。
- `PlanController.generate`（`plan.controller.ts:34-36`）直接 `return this.planService.generatePlan(dto)`，无流式。
- provider 接口 `AiProvider.chat` 返回完整 `ChatResult`（`ai-provider.interface.ts`）；无 `stream` 概念。
- 计划生成 `extraBody` 已关闭 `enable_thinking`（`plan.service.ts` 调用层），故流式 delta 不含 reasoning，干净可用。
- 前端 `/plan` 页经 AI-709「更多」抽屉入口可达；生成走普通 `fetch` POST，拿完整 JSON。

## 3. 接口/能力变更

- `ai-provider.interface.ts` 的 `AiProvider` 新增可选方法：
  - `streamChat(messages: ChatMessage[], options?: ChatOptions & { signal?: AbortSignal }): AsyncIterable<string>` — 逐 delta 产出 `content` 文本；不支持的 provider（如 Mock）可 `throw new AiProviderException('stream 不支持')` 或退化为一次性 yield 全量。
  - 返回 `AsyncIterable<string>` 而非 `ChatResult`，因为流式下 `usage`/`finishReason` 需等流结束才能确定。
- `OpenAiCompatibleProvider.streamChat` 实现：
  - 请求体 `{...base, stream:true, ...this.extraBody, ...options?.extraBody}`；
  - `fetch` 后取 `res.body`（Web `ReadableStream`），按行解析 SSE：`data: {json}\n`，`json.choices[0].delta.content` 累积 yield；遇 `data: [DONE]` 结束；
  - 流结束后解析最后一条 `json.choices[0].finish_reason`（length/stop）与 `usage`，由 `generatePlanStream` 在用。
  - 若 `options.signal` 存在，传入 `fetch` 的 `signal` 支持前端取消。
- `AiCapabilityHub` 透传 `streamChat` 到内部 `chatProvider.streamChat`（若底层不支持 → 抛，由 PlanService 决定降级）。

## 4. 后端实现要点

- **事件协议（SSE）**：定义 `PlanStreamEvent` 联合：
  - `{ type:'start' }`
  - `{ type:'token', text: string }` — 增量文本
  - `{ type:'progress', phase: 'thinking'|'writing'|'done', note?: string }` — 可选的阶段提示（如「正在构思第 1 周…」）
  - `{ type:'done', plan: GeneratedPlan, model: string }` — 校验通过
  - `{ type:'error', code: 'PLAN_INVALID_JSON'|'PLAN_SCHEMA_INVALID'|'PLAN_TRUNCATED'|'AI_ERROR', message: string }` — 校验失败/provider 异常（坚持「出错即抛」，以 error 事件收尾而非静默模板）
- **`PlanService.generatePlanStream(dto): AsyncGenerator<PlanStreamEvent>`**：
  - `yield {type:'start'}`；可选 `yield {type:'progress', phase:'thinking'}`；
  - `for await (const chunk of ai.streamChat(messages, options)) { fullText += chunk; yield {type:'token', text:chunk}; }`
  - 流结束后：`extractJson(fullText)`；失败 → `yield {type:'error', code:'PLAN_INVALID_JSON'}` 并 `return`；
  - `validatePlan(parsed)`；失败 → `yield {type:'error', code:'PLAN_SCHEMA_INVALID', message:errors.join(';')}` 并 `return`；
  - 若流结束测得 `finish_reason==='length'` → `yield {type:'error', code:'PLAN_TRUNCATED'}` 并 `return`；
  - 成功 → `yield {type:'done', plan, model}`。
  - provider 抛错 → 捕获后 `yield {type:'error', code:'AI_ERROR', message:e.message}`（不向上抛，因为 SSE 已无法回 HTTP 状态；错误走事件通道）。
  - `options` 沿用：`extraBody:{chat_template_kwargs:{enable_thinking:false}}` + `maxTokens:6000` + 超时 55s（provider 流式下由 `signal`/fetch 超时兜底）。
- **`PlanController`** 新增 `POST /api/ai/plan/generate/stream`：
  - 返回 `text/event-stream`（`@Header('Content-Type','text/event-stream')` + `Cache-Control: no-cache` + `Connection: keep-alive`）；
  - `for await (const ev of planService.generatePlanStream(dto)) { res.write(`data: ${JSON.stringify(ev)}\n\n`); }`；结束 `res.end()`。
  - 原非流式 `POST /api/ai/plan/generate` **保留**（供 save 流程 / 无 JS 环境 / 测试使用），二者并存。
  - 鉴权口径与原 `generate` 一致（childId 由 body 传，本组接口暂不加 `JwtAuthGuard`，与现有约定一致）。

## 5. 前端实现要点

- `/plan` 页：生成按钮改为调用 stream 端点，`fetch` + `response.body.getReader()` 逐行解析 `data:` 帧：
  - `token` 事件 → 追加到「实时草稿」面板（渐进文本，可附带狐狸老师气泡动画）；
  - `progress` 事件 → 更新阶段提示；
  - `done` 事件 → 切换到结构化计划预览（现有渲染逻辑），启用「保存」按钮；
  - `error` 事件 → 显示错误提示 + 重试按钮（与现有「出错即抛」一致，前端不再白屏或静默）。
- 取消：生成中提供「取消」按钮，`AbortController.abort()` 中断流（后端 `signal` 透传到 provider fetch）。
- 进度体感：顶部进度条 + 「狐狸老师正在构思第 N 周…」（可基于已收到的 `week` 关键词粗估，或仅用「正在生成…」脉冲）。
- `src/lib/api.ts` 新增 `generatePlanStream(dto, onEvent, signal)` 封装（纯逻辑，需单测）。
- i18n 补齐 `Plan.streaming` / `Plan.cancel` / `Plan.generatingWeek` 等键（中英）。

## 6. 关键决策（待开工时确认）

- **展示内容**：方案 A（推荐）直接展示 AI 原始逐字文本（含 JSON 草稿，带「正在生成…」脉冲，终态切结构化）——实现简单、最贴近聊天体感；方案 B 解析中间态周标题做精致进度（复杂、需稳定前缀约定，不推荐）。
- **流 vs 非流并存**：保留原 `generate` 端点（兼容 + 测试简单），新增 `generate/stream`；前端默认走 stream，stream 不可用时（极旧浏览器）回退 `generate`。
- **JSON 仍末端校验**：明确「流式只展示、不解析中间态」，避免半成品 JSON 崩溃；此点与 AI-204「出错即抛」口径一致。
- **504 缓解**：流式持续吐帧使 Vercel 连接存活，但**总时长仍须 < 60s**；若单模型极慢仍可能超时，必要时配合 AI-204 的 `maxTokens`/thinking 关闭 + 模型选型。

## 7. 验收标准

- 后端：调 `generatePlanStream` 用 Mock provider（一次性 yield 完整合法 JSON），消费端依次收到 `start → token(s) → done(plan)`；Mock 产出非法 JSON → 收到 `start → token(s) → error(PLAN_INVALID_JSON)` 且**不**抛未捕获异常（事件通道收尾）。
- `OpenAiCompatibleProvider.streamChat` 单测：mock `fetch` 返回 SSE 流（`data: {choices:[{delta:{content}}]}\n\ndata: [DONE]`），断言逐 delta yield 且累积正确；`finish_reason:'length'` 在第终帧可得。
- `PlanController` `/generate/stream` 集成测试：用 supertest 拉流，断言响应头 `text/event-stream` + 事件序列含 `done` 或 `error`。
- 前端 `generatePlanStream` 封装单测（mock fetch Reader，断言 onEvent 按 token/done 触发、abort 中断）。
- 前端 `/plan` 页 E2E（BDD）：点击生成 → 看到实时草稿文本出现 → `done` 后结构化预览 + 保存按钮可点；注入非法 JSON 时显示错误与重试（语言无关断言，CI 跑 zh）。
- 后端 `tsc --noEmit` 0 + 前端 `next build` 成功 + 自带 BDD/E2E（见置顶质量约定）。

## 9. 实施备注（2026-08-18 落地）

- **Provider 链透传**：`AiProvider` 接口新增可选 `streamChat?`；`OpenAiCompatibleProvider`（真实 SSE fetch + `ReadableStream` 行解析，`finish_reason:'length'`→`AiProviderException('PLAN_TRUNCATED')`，`AbortError`→`ABORTED`）→ `ChatProvider`（不支持退 Mock）→ `MockAiProvider`（一次性 yield `CHAT_FALLBACK`）→ `AiCapabilityHub`（透传 chatProvider）→ `UsageLimitedAiProvider`（配额守卫后透传，缺失→`STREAM_UNSUPPORTED`）→ `LoggedAiProvider`（审计透传）。接口层保持可选，既有仅实现 `chat` 的测试桩不破。
- **后端事件协议**：`PlanStreamEvent` 联合（`start`/`token`/`progress`/`done`/`error`）；`PlanService.generatePlanStream` 累加 fullText、`extractJson`+`validatePlan` 末端校验、`useTemplate` 直出 `done(model:'template')`、provider 异常/截断映射为 `error` 事件（不向上抛）；`PlanController.generateStream` 以 `text/event-stream` 逐帧 `res.write('data: '+JSON+'\n\n')`，`req.on('close')`→`AbortController.abort()` 透传 provider fetch（缓解 Vercel 504 白屏）。
- **前端**：`src/lib/api.ts` 新增 `generatePlanStream(dto,onEvent,signal)` + 纯函数 `consumeSse(body,onEvent)`（SSE 行解析，跨 chunk 帧边界、跳过非 JSON 控制行、AbortError 静默返回；`res.body` 缺失自动退化 `generatePlan` 合成 start→done）；`/plan` 页 `PlanContent` 改为流式：生成按钮调 `generatePlanStream`，`token`→`PlanDraftPanel` 渐进文本、`progress`→阶段提示、`done`→`PlanPreview` + 启用保存、`error`→`PlanStreamError`+`retry-stream`、取消按钮 `cancel-stream`（`AbortController`）；`src/lib/types.ts` 新增 `PlanStreamEvent`/`PlanStreamErrorCode`；i18n 补 `streaming/thinkingPhase/writingPhase/streamHint/generatingWeek/cancel/canceled/streamError/retry`（中英）。
- **测试**：后端 `plan.service.spec` 7 例（含 useTemplate/无效 JSON/坏 schema/截断/流异常/无 streamChat→STREAM_UNSUPPORTED）+ `openai-compatible.provider.spec` 4 例 SSE（delta 累积/多行数据+跳过非 JSON/`finish_reason:length`→PLAN_TRUNCATED/无 chat 能力→UnsupportedMethodError）；前端 `api-stream.spec` 8 例（consumeSse 跨 chunk/跳过心跳、generatePlanStream 正常序/error 事件不抛/非 ok/无 body 退化/abort 不抛 error）；新增 E2E `plan-stream.feature`（成功走 stream 端点→预览；首次失败重试成功→预览），扩展 `plan.ts` POM（`streamGenerate`/`mockStreamValidPlan`/`mockStreamErrorThenValid`/`submitGeneration`/`clickRetry`）+ `plan.steps.ts`；既有 `mockGeneratePlan` 改为 mock `/generate/stream`（结构不变）以保证 plan-wizard/plan-display/plan-courses/plan-progress 既有场景继续封闭。
- **E2E 限制（如实说明）**：本机 Playwright 1.62 的 `route.fulfill` 将 body 一次性转 base64 响应（不支持分块流式），故 mock 以单串 SSE 帧返回，浏览器完整解析后由 `done`/`error` 事件驱动终态——渐进草稿的「逐帧渲染」窗口（React 同任务批量提交）在本机 e2e 无法稳定观测；该渲染逻辑由前端 `consumeSse` 单测（事件按序产出）+ 组件行为保证，e2e 仅验证「走 stream 端点 → 终态正确」。全量 E2E 实跑交 CI `e2e` job 兜底（user-accepted-ci，本机 next dev 受限，见项目护栏）。
