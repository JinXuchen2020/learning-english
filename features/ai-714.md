# AI-714 — Provider 配置必须指定 model + 基于具体 model 的能力多选验证

> 状态: done | 栈: node-ts (Next.js 前端 + NestJS 后端) | 分支: feat/ai-714
> 来源: 用户决策（2026-08-17）— AI-705 让家长自由增删 AI provider，AI-713 把 provider 去 env 化。
> 但当前添加 provider 时**没有 model 字段**，而能力（chat/vision/stt/tts/pronunciation）是**模型级别**的属性：
> 同一个 OpenAI 兼容 endpoint 下，`gpt-4o` 有 vision 但 `gpt-4o-mini` 可能无；`tts-1` 有 tts 但 `gpt-4` 无。
> 因此必须先指定 model，再勾选该 model 实际拥有的能力；保存时**按该具体 model 真发请求验证所有勾选能力**，
> 任一能力不被该 model 支持 → **硬拒绝保存**。

## 1. 目标

- 添加/编辑 provider 时，**`model` 为必填字段**（如 `gpt-4o` / `tts-1` / `whisper-1`）。
- 能力（`chat`/`vision`/`stt`/`tts`/`pronunciation`）为**多选**，可勾 0..N 个。
- **保存前验证**：对每个勾选的能力，用当前 `model` 真发最小请求（而非仅声明），确认该 model 真有此能力。
- 任一勾选能力验证失败 → **400 硬拒绝保存**（后端 create/update 双重保险 + 前端保存前预览分能力结果）。
- 前端聊天页：当 `ttsUrl` 为空（无论后端 TTS 是否配置/失败）时，**永远用浏览器 Web Speech API 朗读兜底**（方案 A），保证任何环境都有声音。
- `EdgeTtsProvider`（本地 Python 兜底）仅在探测到 Python 时挂载到 TTS 链末尾；Vercel（无 Python）自动不挂。

## 2. 接口契约

### 后端

**DTO 变更（`provider-config.dto.ts`）**
- `CreateProviderConfigDto`：
  - 新增必填 `@IsString() @MaxLength(120) model: string`（位于 `type` 之后、`baseUrl` 之前）。
  - 移除已废弃的 `ProviderModelsDto` / `models?` 字段（统一为单一 `model` 字段驱动所有能力）。
  - `capabilities?: ProviderCapabilityDto[]` 保持可选（空 = 表示该 provider 不对外声明任何能力，纯占位）。
- `UpdateProviderConfigDto`：
  - 新增可选 `@IsString() @MaxLength(120) model?: string`（换模型时传，传则重新验证能力）。
  - 同上移除 `models?`。

**Entity 变更（`provider-config.entity.ts`）**
- `ProviderConfig` 新增 `@Column({ type: 'varchar', length: 120 }) model: string`（必填，向后兼容：seed 系统 provider 须带 `model`）。
- 移除 `ProviderModels` 接口 / `modelsJson` 列（已合并进单一 `model` 字段）。
- `capabilitiesJson` 列保留（存勾选的能力数组）。

**新增验证端点**
- `POST /api/provider-config/validate`（不落库）：入参同 `CreateProviderConfigDto`（含 `model`+`capabilities`），返回
  ```json
  { "ok": false, "results": { "chat": {"ok":true}, "tts": {"ok":false,"reason":"model tts-1 不支持..."} } }
  ```
  —— 供前端保存前预览分能力结果，不阻断。

**create / update 行为变更（`provider-config.service.ts`）**
- 调用 `validateCapabilities(config)`：对每个勾选能力，用 `config.model` 真发最小请求：
  - `chat` → 极短 messages ping（1 轮）。
  - `vision` → 用该 model 发 1×1 png（base64 极小图）。
  - `tts` → 用该 model `synthesize('hi')`（取前若干字节即可，验证非 4xx/5xx 且返回音频）。
  - `stt` → 用 `whisper-1` transcribe 静音 wav（测 endpoint 连通 + 鉴权，不限 model）。
  - `pronunciation` → openai-compatible 通用端点不支持，直接标 `ok:false`（需在专有 provider 才支持）。
- 任一失败 → `BadRequestException`（硬拒绝保存），message 列出失败能力+原因。
- `buildProvider(config)`：把 `config.model` 注入 provider（不再分 chat/vision/tts 三个模型字段）；`capabilities` 非空时，未声明能力的方法开头抛 `UnsupportedMethodError`，让兜底链自动跳过该 provider。

### 前端

**`src/lib/api.ts`**
- `ProviderConfig` 类型新增 `model: string`；`CreateProviderConfigDto`/`UpdateProviderConfigDto` 类型同步。
- 新增 `validateProviderConfig(dto): Promise<{ok:boolean; results: Record<string,{ok:boolean;reason?:string}>}>` 调用 `POST /provider-config/validate`。

**`src/app/[locale]/parent/settings/page.tsx`**
- provider 表单新增「模型」**必填输入框**（位于 API Key 下方、能力多选上方），placeholder 示例 `gpt-4o` / `tts-1` / `whisper-1`。
- 保存前调用 `validateProviderConfig` 展示分能力 ✓/✗ 结果；保存仍走 create/update（后端硬拒绝双重保险）。
- 能力为多选 checkbox（已有），文案提示「勾选该模型实际支持的能力」。

**`src/app/[locale]/chat/page.tsx`（方案 A 兜底）**
- `res.ttsUrl` 为空时：渲染「浏览器朗读」按钮，点击调用 `speakText(res.replyText, { lang: 'en-US' })`（来自 `src/lib/speech.ts`）。
- 保留「(这次没有语音)」提示，旁边加朗读按钮。

## 3. 数据模型

- `provider_configs` 表：
  - 新增列 `model varchar(120) NOT NULL`。
  - 移除列 `models_json`（如已存在，迁移 drop；SQLite/Postgres 兼容处理）。
- 种子系统 provider（智谱）须带 `model`（如 chat/vision 用 `glm-4.7-flash` 类；tts 用其 tts 模型）——seed 脚本补齐。
- 能力存 `capabilities_json`（数组，如 `["chat","vision"]`）。

## 5. 风险点

- **破坏性 schema 变更**：`models_json` 列移除 + `model` 列 NOT NULL。本仓库用 TypeORM `synchronize`，需确认无现存数据依赖（provider_configs 仅 seed 系统行 + 测试行，均可控）；迁移脚本清理。
- **STT model 固定 `whisper-1`**：多数 openai-compatible 端点 STT 用 `whisper-1`，与主 chat model 不同。验证 STT 时用 `whisper-1` 而非 `config.model`（避免把"模型名错"误判为"无能力"）。
- **TTS 端点差异**：部分国产端点 TTS 路径/字段与 OpenAI 不完全一致，验证时仅校验非错误响应 + 有音频返回，不校验音色。
- **Vercel 无 Python**：`EdgeTtsProvider` 条件挂载已规避；但需确认 `edgeTtsAvailable()` 探测不会在 Vercel 抛错挂起（超时兜底）。

## 6. 测试计划（硬约束 #6）

### 单元测试
- `openai-compatible.provider.spec.ts`：构造含 `capabilities:['chat']` 的实例 → `synthesize()` 抛 `UnsupportedMethodError`；`chat()` 正常。
- `provider-config.service.spec.ts`：
  - `validateCapabilities` mock `fetchFn`：chat/tts/vision 全 200 → 返回全 ok；tts 返回 400 → 该能力 `ok:false` 且整体可识别失败。

  - `create` 流程：capabilities 验证失败 → 抛 `BadRequestException`。

### BDD/E2E 用户旅程
- 场景：家长进入设置 → 添加 AI provider → 填名称/类型/Base URL/API Key/**模型(gpt-4o)** → 勾选 chat+vision → 点「验证」显示 ✓✓ → 保存成功。
- 场景：家长填模型 `gpt-4` 却勾选 tts → 保存被拒，页面提示 tts 验证未通过。
- 场景：聊天页某条消息无音频 → 出现「浏览器朗读」按钮 → 点击触发朗读（mock SpeechSynthesis 或断言按钮存在）。
