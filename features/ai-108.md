# AI-108 — AI 调用日志（审计 + 可检索）

> 状态: in-progress | 栈: node-ts (NestJS 10 + TypeORM) | 分支: feat/ai-108
> 依赖: AI-106（重试/降级）、LOG-101（统一 Logger + 日志文件）、AI-107（每日配额外壳）
> 前置: 当前链 feat/ai-106←feat/ai-107←feat/ai-108（在 feat/ai-107 上建新分支）

## 1. 目标
为每次 LLM 调用留下**可检索、可审计**的记录：谁（userId）、哪个模块（moduleTag）、走了哪个 provider、消耗多少 token、耗时多少、成功/失败、输入/输出摘要（敏感内容截断）。记录同时落 **LOG-101 结构化日志文件**（即时 grep）与 **`ai_call_logs` 表**（按用户/日/模块聚合做成本审计）。便于排查线上问题与统计 AI 成本，且不泄露儿童隐私（输入 prompt / 输出文本一律截断）。

## 2. 接口契约
### 后端（provider 装饰器，无新 HTTP 路由）
- 新增 `LoggedAiProvider implements AiProvider`：最外层外壳，包裹 `UsageLimited(Retryable(inner))`。
  - 每个方法调用前计时 → 执行内层 → 成功/失败后写入一条审计记录（logger + 表），再返回/抛出。
  - `name` 透传内层 provider，消费方契约不变。
- 新增 `AiCallLogService.record(entry)`：best-effort 落库 `ai_call_logs`，DB 写失败吞异常（审计不得影响主流程）。
- 新增 DI token `AI_MODULE_TAG_RESOLVER_TOKEN`（`() => string`，默认 `'global'`），与 AI-107 的 `USER_ID_RESOLVER_TOKEN` 一致，供未来 AI 控制器注入请求级模块标识。

### 审计记录字段（logger meta + 表列）
- `provider` / `operation`（chat|chatWithImage|transcribe|assessPronunciation|synthesize）
- `userId`（来自 `USER_ID_RESOLVER_TOKEN`，默认 `'anonymous'`）
- `moduleTag`（来自 `AI_MODULE_TAG_RESOLVER_TOKEN`，默认 `'global'`）
- `durationMs`、`status`（`'ok'|'error'`）、`errorMessage`（截断）
- `tokens`: `{ promptTokens, completionTokens, totalTokens }`（仅 chat 类有 usage，其余 0）
- `requestSnippet` / `responseSnippet`：**敏感内容截断**（默认前 200 字符 + `…`）。

## 3. 数据模型
- 新增实体 `AiCallLog` → 表 `ai_call_logs`：
  - `id` uuid 主键、`userId`(varchar 64, default 'anonymous')、`provider`(varchar 32)、
    `operation`(varchar 32)、`moduleTag`(varchar 32, default 'global')、
    `promptTokens`/`completionTokens`/`totalTokens`(int, default 0)、
    `durationMs`(int, default 0)、`status`(varchar 16)、
    `errorMessage`(varchar 255, nullable)、`requestSnippet`/`responseSnippet`(text, nullable)、
    `createdAt`(CreateDateColumn)。
- 注册进 `config/database.config.ts` 的 `appEntities`（dev `synchronize` 自动建表），并在 `AiModule` 内 `TypeOrmModule.forFeature([AiUsage, AiCallLog])`。
- **不写迁移**：沿用项目既有 `synchronize` 模式（与 AI-107 一致）。

## 4. 验收标准
- [ ] 每次 LLM 调用（含被配额拦截/失败）都有一条可检索日志（logger 文件 + 表）。
- [ ] 输入/输出摘要被截断（默认 200 字符），不把儿童原始录音/长文本全量写入日志或表。
- [ ] 审计写库失败不阻断主 AI 调用（best-effort）。
- [ ] 覆盖率：新增有逻辑分支源码单测全绿（≥ 90% stmts / 70% branches 全局基线）。
- [ ] `nest build` / `tsc` 0 错误；jest 全绿；pre-commit 质量门强执通过。

## 5. 风险点
- **敏感信息泄露**：prompt/response 含儿童对话与音频转写文本 → 一律截断摘要，绝不写原始音频 base64 / 整段文本。多模态场景只记 `prompt + [image:<mime>]`，不记 base64。
- **审计写库拖慢主流程**：`record` 全程 best-effort（吞异常、不 await 阻塞关键路径过久）——当前为 await 但内部 try/catch 保证不抛。
- **重复计数**：日志记录放在最外层，一次用户请求 = 一条审计（含重试总耗时），不在 retry 层内部重复记录。
- **无 AI 控制器**：当前 `userId`/`moduleTag` 默认 `'anonymous'`/`'global'`；未来 AI-20x/30x/40x 控制器需注入请求级 resolver 实现按登录用户/模块隔离。
